# 太空饭否分发路线决策指南

- Executor: codex
- Run ID: `sf-distribution-20260717-01`
- Timestamp: 2026-07-17T16:00:59+08:00
- Checkpoint: decision-guide-complete
- 面向读者：希望继续维护太空饭否、但不想亲自处理代码和复杂发布工具的人

## 先说结论

两条路线都可以准备，但不应同时维护两套完整代码。

- **路线 A：独立发布到 Chrome Web Store。** 保留太空饭否的全部能力，用户安装和更新最省事；代价是一次性开发者注册费、首次上架准备、Google 审核，以及今后的持续维护责任。
- **路线 B：免费分发。** 完整功能继续以“加载已解压扩展”的方式提供；再把纯美化部分单独做成用户脚本。它不需要商店开发者账户，但安装和更新没有商店方便。

推荐的准备顺序是：先完成两条路线共用的合规和发布基础，再决定是否付款上架。这样即使最后放弃商店，已经做完的工作仍然能提高免费版本的安全性和可维护性。

## 我们现在面对的真实情况

1. 原 Chrome Web Store 条目已经因为 Manifest 没有及时更新而被下架。
2. 接受 Manifest V3 PR 的仓库维护者不是饭否官方，也不掌握原商店条目的发布权限。
3. 因此，本项目不能把“仓库接受 PR”理解成“官方会重新上架”。
4. 如果我们自己发布，它会成为一个新的独立商店条目，不能自动继承原条目的用户、评价和更新关系。
5. 当前项目已经是 Manifest V3，但**还没有达到可以原样提交商店的状态**：生产版本仍会从 `google-analytics.com` 加载远程 JavaScript。Chrome Web Store 明确禁止 Manifest V3 扩展执行这种远程托管代码，提交前必须删除或改成本地、合规的实现。

## 两条路线的直观比较

| 你关心的事情 | 路线 A：自己上架商店 | 路线 B：免费分发 |
|---|---|---|
| 是否付费 | 必须支付一次性开发者注册费；公开文档未写死当前金额 | 不需要商店开发者注册费 |
| 用户安装 | 最简单，商店里点击安装 | 完整版要解压、开启开发者模式、选择目录；美化脚本要先装脚本管理器 |
| 自动更新 | 商店负责自动更新 | 完整版通常需要手动替换文件并重新加载；用户脚本可以由脚本管理器检查更新 |
| 能否保留全部功能 | 可以 | 离线扩展可以；单独的用户脚本不可以 |
| 首次准备工作 | 较多：账户、费用、隐私、素材、权限说明、审核 | 较少：发布包、安装图文、更新说明、数据迁移 |
| 后续维护 | 必须看邮件、处理政策提醒和审核问题 | 不受商店审核，但要回答安装和手动更新问题 |
| 适合谁 | 希望普通用户一键安装，并愿意长期维护 | 自己使用、小范围分享、明确不愿付费或不想承担商店责任 |

## 路线 A：独立发布到 Chrome Web Store

### 钱的问题

Google 官方现在只公开确认：注册 Chrome Web Store 开发者账户前必须支付**一次性注册费**。开发者协议写明金额由 Google 决定，公开说明页没有固定列出当前数字。因此：

- 可以确认“要付费”；
- 可以确认“不是官方文档所述的年费”；
- 过去常见的 5 美元不能当作 2026 年已经核实的当前价格；
- 实际金额应以你登录开发者后台后看到的付款页面为准；看到金额之前不必付款。

### 没有一个“从零开始、全部代办”的官方 CLI

Google 提供 Chrome Web Store API v2，也给出了 `curl` 命令，但它不是面向普通用户的一键发布工具。

官方 API 当前明确适合做这些事情：

- 给已有商店条目上传新版安装包；
- 提交审核或发布已经上传的版本；
- 查询上传、审核和发布状态；
- 取消审核提交；
- 对符合条件的扩展调整分批发布比例。

它不能替你省掉这些首次人工步骤：

- 注册开发者账户并付款；
- 开启 Google 账户两步验证；
- 在后台创建第一个条目并确认开发者身份；
- 填写商店介绍、截图、隐私页、权限用途和分发范围；
- 对声明、协议、最终提交和发布承担责任。

此外，配置官方 API 本身还要建立 Google Cloud 项目、启用 API、配置 OAuth 同意屏幕，并取得 Client ID、Client Secret、Refresh Token、Publisher ID。对于第一次发布，这通常比直接使用网页后台更复杂。

旧版 API v1 虽然还有创建条目的接口，但它已经弃用，并将在 **2026-10-15** 停止支持。为了一个新项目接入即将退役的接口，只会多做一次迁移，不建议采用。

社区里有维护中的 `chrome-webstore-upload-cli`，可以包装官方 API 来上传和发布，但它同样需要上述 OAuth 凭据和已经存在的商店条目。它适合“第一次成功发布以后，自动发布后续版本”，不适合帮非程序员完成首次开户和表格填写。

### agent-browser 能帮到哪里

可以把 agent-browser 当成“有人陪你操作网页并代填大部分草稿”，不能把它当成开发者账户的主人。

**可以由代理准备或辅助的部分：**

- 打开正确的后台页面，解释每一栏在问什么；
- 根据代码审计结果起草扩展简介、单一用途、权限理由和数据使用说明；
- 准备并检查图标、截图、安装包、隐私政策链接；
- 在你已经安全登录后填写非敏感表单草稿；
- 上传准备好的 ZIP，读取页面校验结果；
- 审核前逐项检查遗漏，并把退回原因翻译成普通语言。

**必须由你本人完成或最后确认的部分：**

- 输入 Google 密码和两步验证码；
- 输入付款资料并确认付款；
- 身份验证、法律协议和开发者声明；
- 确认隐私声明准确反映你愿意承担的责任；
- 点击“提交审核”“发布”“取消发布”等会改变外部状态的最终按钮。

Google 也可能触发验证码、异常登录保护或重新认证。这时浏览器自动化会停下，由你手动完成，再继续后面的非敏感步骤。不要把密码、验证码、银行卡资料、Client Secret 或 Refresh Token 写进聊天、仓库或截图。

### 第一次发布的实际流程

#### 第 1 阶段：我们先把项目准备好，不需要你的 Google 账户

1. 删除当前远程加载的 Google Analytics JavaScript，并确认生产包不再执行远程代码。
2. 审计 `tabs`、`notifications`、`contextMenus`、`storage`、`offscreen`、`scripting`、`alarms`、`identity` 等权限，删除不需要的权限，为保留项写普通人能看懂的理由。
3. 写隐私政策，明确饭否登录、OAuth、页面内容、设置、通知和本地数据分别怎样处理。
4. 确定独立项目名称和说明，避免让用户误以为它是饭否官方重新上架。
5. 准备图标、至少一组真实截图、短介绍、详细介绍、支持入口和版本说明。
6. 生成发布 ZIP，并完成测试、构建、真实登录态检查和敏感信息扫描。

#### 第 2 阶段：你处理账户和付款，我在旁边解释

1. 准备一个长期可访问、会持续收邮件的 Google 账户；Google 官方建议发布账户使用专门邮箱。
2. 开启两步验证。
3. 打开 Chrome Web Store Developer Dashboard。
4. 阅读页面显示的实际注册费；只有你决定接受后才付款。
5. 完成开发者资料和可能出现的身份验证。
6. 由你本人判断并声明 Trader（经营者）或 Non-Trader（非经营者）；如果选择 Trader，可能还要验证并公开法定姓名、电话和地址等信息。这是法律身份判断，不能由代码代理替你决定。

#### 第 3 阶段：共同填写第一个条目

1. 在网页后台点击新增条目，上传准备好的 ZIP。
2. 填写 Store Listing：名称、简介、详细描述、图标、截图和支持信息。
3. 填写 Privacy：单一用途、每项权限理由、数据使用和远程代码声明。
4. 选择 Distribution：先使用受信任测试者或非公开测试，再决定公开发布。
5. 由你检查并点击提交审核。建议使用“审核通过后暂不自动发布”，避免通过后立刻面向所有人。

#### 第 4 阶段：处理审核

官方说明通常是几天，但可能长达几周；官方在 2026 年 4 月还特别提示提交量上升、审核延长。新开发者、新扩展、敏感权限和较多代码都可能增加审查时间。

如果被退回，先根据明确的违规编号修复，再重新提交。不要反复盲目提交同一个包。

#### 第 5 阶段：第一次发布成功后再自动化

第一次发布完成后，可以再配置官方 API 或第三方 CLI，让后续流程变成：构建 → 打包 → 上传 → 查询状态。即使使用 CLI，建议仍保留“由你确认最终发布”的保险闸，避免一次错误构建直接推给所有用户。

### 商店路线当前的主要门槛

按优先级排列：

1. **远程代码门槛：** 当前 Google Analytics 远程脚本必须移除或替换。
2. **隐私门槛：** 项目有登录/OAuth、页面交互和本地存储，必须把数据处理说清楚。
3. **权限门槛：** 权限较多，要逐项证明与用户可见功能直接相关。
4. **身份门槛：** 新条目必须明确是社区维护版本，不能暗示饭否官方背书。
5. **迁移门槛：** 新商店条目不会继承旧条目用户，开发者模式用户也需要安装和本地数据迁移说明。
6. **维护门槛：** 上架以后必须持续查看开发者邮箱，不能再次因为无人响应政策提醒而下架。

## 路线 B：免费分发

免费路线最好拆成“完整功能版”和“轻量皮肤版”，而不是把整个项目强行改写成一个脚本。

### B1：完整功能版——加载已解压扩展

用户实际操作是：

1. 下载我们准备好的发布压缩包并解压到一个固定目录。
2. 打开 `chrome://extensions`。
3. 开启右上角“开发者模式”。
4. 点击“加载已解压的扩展程序”，选择解压目录中的扩展文件夹。
5. 以后更新时，在同一个固定目录中替换文件，再回到扩展页点击“重新加载”。

优点：不付费，而且保留完整功能，包括桌面通知、扩展图标、右键菜单、设置、后台定时任务、OAuth 和本地数据。

缺点：安装步骤对普通用户不够友好；Chrome 会提示这是开发者模式扩展；更新不能像商店一样自动完成。

Chrome 官方不允许普通 Windows 和 macOS 用户像安装普通软件一样，从个人网站直接安装并自动更新自托管 CRX。除企业策略等受管环境外，免费分享完整版的现实方案仍然是加载已解压目录。

#### 这条路线必须先解决的数据问题

当前 Manifest 没有固定 `key`。如果用户每次把新版本解压到不同目录，Chrome 可能把它识别为另一个扩展，本地设置和头像消消乐战绩看起来就会“丢失”。

准备免费完整版时应同时完成：

- 提供设置和安全本地记录的导出/导入；
- 明确要求使用同一个固定安装目录；
- 评估是否为开发者模式版本固定扩展 ID；
- 不导出 OAuth Token、Cookie、签名密钥或浏览器会话资料。

### B2：轻量皮肤版——用户脚本

用户脚本适合完成：

- 字体、颜色、留白、背景和卡片样式；
- 侧栏布局、头像墙、装饰元素；
- 页面内按钮和轻量交互；
- 对饭否页面已有 DOM 的显示、隐藏和重新排列。

它不适合完整替代：

- Chrome 桌面通知和后台轮询；
- 扩展图标行为；
- 浏览器右键菜单；
- offscreen 音频；
- `chrome.identity` 授权流程；
- 扩展设置同步和后台 Service Worker；
- 与完整扩展完全相同的存储和跨标签页行为。

使用者需要先安装 Tampermonkey、Violentmonkey 等用户脚本管理器，再安装我们的 `.user.js`。脚本可以放在 GitHub 或稳定网址上，并通过版本号及 `@updateURL` / `@downloadURL` 让脚本管理器检查更新。

为了避免维护两套越来越不同的产品，轻量脚本应只承诺“美化与页面增强”，不承诺复制完整太空饭否。适合从字体、背景、布局和装饰开始，之后只迁移确实适合网页上下文的功能。

### 为什么不照搬 Codex Dream Skin 的 CDP 启动脚本

Codex Desktop 是封装了 Chromium 的桌面应用，外部脚本需要通过调试协议找到它的渲染进程。饭否本来就是 Chrome 里的普通网页，用户脚本或扩展内容脚本已经能直接修改页面。

如果我们也要求用户通过 CDP 启动 Chrome，就会额外带来：

- 每次必须用特殊命令启动浏览器；
- 本机要开放调试端口；
- 脚本需要寻找并连接正确的页面；
- 对非程序员更难排错；
- 得到的视觉能力并没有比用户脚本更多多少。

所以 CDP 适合作为技术实验，不适合作为本项目的普通分发方式。

## 按你的实际情况，哪些工作由谁承担

| 工作 | 我/其他代码代理可完成 | agent-browser 可辅助 | 你必须完成 |
|---|---:|---:|---:|
| 审计代码和权限 | 是 | 否 | 只需看结论 |
| 删除远程代码、准备发布包 | 是 | 否 | 最终验收 |
| 写商店文案、权限理由、隐私政策草稿 | 是 | 可填表 | 确认内容真实 |
| 准备图标和截图 | 是 | 可截图/上传 | 选择最终版本 |
| 注册 Google 开发者账户 | 否 | 可导航解释 | 是 |
| 密码、两步验证、付款 | 否 | 应暂停 | 是 |
| 创建条目、填写后台页面 | 可准备 | 是 | 检查 |
| 点击提交审核或最终发布 | 不应擅自执行 | 应停在按钮前 | 是 |
| 处理审核退回 | 是 | 可读取后台 | 决定是否继续 |
| 后续版本 CLI 自动上传 | 是 | 通常不需要 | 保管账户和密钥 |
| 免费版安装包和图文说明 | 是 | 可验证流程 | 试用确认 |
| 轻量用户脚本 | 是 | 可在真实页面验收 | 决定美化范围 |

## 不浪费工作的准备顺序

无论最终选哪条路线，先做下面五件共用工作：

1. 清除远程 Google Analytics 代码，并重新审计所有外部请求。
2. 审计并缩减扩展权限，形成每项权限的普通语言说明。
3. 增加安全的数据导出/导入，并解决开发者模式更新时的扩展 ID 连续性。
4. 写好“社区维护、非饭否官方”的身份说明和隐私政策。
5. 形成可重复的测试、构建、打包和真实登录态验收流程。

完成以后再分叉：

- 选择商店：准备商店素材，你查看实际费用，注册账户并走首次审核。
- 选择免费：发布稳定目录包、图文安装指南和更新指南；另做一个范围明确的皮肤用户脚本。

这个顺序的回退成本最低：如果商店费用、验证或审核让你不舒服，可以立刻停在免费路线；已完成的安全、隐私和数据迁移工作不会浪费。

## 你可以怎样做最后决定

选择商店路线，需要同时接受下面四件事：

- 愿意支付后台实际显示的一次性注册费；
- 愿意用一个长期邮箱接收政策和审核通知；
- 希望让非技术用户一键安装和自动更新；
- 接受首次上架不是“上传 ZIP 就结束”，以后仍要维护。

选择免费路线，只需要接受下面三件事：

- 用户安装步骤会更多；
- 完整版更新主要靠手动替换文件；
- 用户脚本只是轻量皮肤，不等于完整扩展。

如果现在还不确定，最稳妥的默认选择是：**先把免费完整版本做可靠，同时完成商店共用的合规准备；暂不注册、不付款、不提交。** 等准备完成后，你再打开后台看实际金额和页面要求，做一次不会被技术细节干扰的决定。
